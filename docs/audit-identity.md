# 审计身份与执行来源

审计事件保留 `user_id` 原始标识，以 `actor_kind`（user/tool/system/unknown）区分人员、工具、系统任务与待核验身份。`actor_name` 由数据库写入触发器从受保护的 `user_roles` 解析，覆盖调用方提交的同名字段；不是前端或脚本自行声称的身份。此快照不随之后的目录改名或删除而改变，不改变原有认证、RLS 或审计写入权限。

旧日志中的 `codex` 明确表示 Codex 工具执行，`system` 表示未记录个人登录身份的系统任务，具体入口仍看来源字段，不能据此推定是自动运行还是人工维护。其他没有证据的标识不得推定为系统或某个员工；显示“身份待核验”，进入“需关注”，技术详情保留原始用户标识、操作类型、来源和完整操作信息。用户目录读取失败单独提示，不伪装成账号不存在。

历史人员日志继续通过目录解析，不将今天查得的姓名冒充历史操作时快照。历史工具／系统日志只补充分类型和工具名称，原始 ID、动作、时间、批次及业务证据不改写；不根据批次授权说明把工具记录改署到授权人名下。

## 写入入口

- 网页／API 沿用现有可信会话和共享审计入口；人物归属从服务端身份产生。
- `scripts/sales-materials/ingest.mjs --target supabase --apply` 必须显式提供 `--actor-user-id 管理员UUID`。任何业务或 Storage 写入之前检查账号存在且角色为 `admin`／`super_admin`；失败或目录不可用时终止。该账号是受信任维护操作声明的操作账号，不代表浏览器在线登录，日志保留 `request_source=server` 与 `details.executor=codex`。
- 其他维护 SQL／脚本也需按上述语义保留人员与工具的区别，不创造伪员工账号。未知执行者仍记审计并告警，不能为了显示正常而改署“系统”，也不能丢弃业务审计。
- 新增操作类型同时补中文描述、标签和相关分类；持续回归检查应用与维护脚本中的字面量动作。动态动作及外部 SQL 仍需在代码审阅／执行前核验。

## 升级与回退

先应用 `20261102063824_audit_actor_identity.sql`，再部署网页。网页的“需关注”查询使用新列，反向顺序会导致查询失败。迁移只添加身份列及内部写入触发器，并分类旧工具／系统与无法解析身份，不修改业务数据或用户目录。

回退应用可恢复旧网页；新列保留，不删除已产生的身份快照。若需暂停快照触发器，作为单独数据库维护操作处理，不通过删除历史审计恢复。

持续回归：`npm test` 的身份展示与动作覆盖；Verify 的资料导入校验；真实 PostgreSQL 17 的审计身份、成交编辑和楼宇身份触发链。具体证据见 [本次验证](verification/audit-identity-20261102/README.md)。生产迁移、发布和远端 CI 状态另行记录，不能从本地通过推定上线。
