# 成交转交安全修复与发布说明

状态：第一批本地实施，尚未发布。范围仅全系统排查 F09/F10 及其必要的
并发、重复请求、结果确认与审计保护。不修改历史归属、旧数据、既有RLS、
现有触发器或业务字段口径；不包含全局改密／停用机制改造。

## 实际执行路径

成交工作区保存最小待确认请求（账号、记录、目标、原归属、原时间、请求ID）
→ 已有 HTTP 接口验证真实 Token／角色／模拟身份只读 → 只允许 service_role
调用的 `transfer_lease_submission_v1` → 事务锁定当前账号与接收人状态、记录，
验证原归属和完整时间戳 → 只改 submitter_id／submitter_name → 既有 UPDATE
审计＋TRANSFER_SUBMISSION 审计＋私有结果收据一起提交 → 回读工作区。

收据按真实操作者＋请求ID隔离，重放需全部参数一致。重放只是确认原操作
已经完成，不保证当前归属仍与旧收据相同；当前状态必须回读。新的合法转交
不会因旧请求重试被覆盖。原始来源、original_*、面积、租金、期间等均保留。

接收人资格保持已有 `/api/brokers` 契约：editor、有非NULL email、中文名
非NULL且不为“测试账号”、Auth账号存在且未删除／未停用。显示名来自档案，
客户端 name／actor 不被信任。账号资格在事务内重新验证并锁定到提交。
资格值必须来自同一个按user_id排序、对Auth与档案行本身加FOR SHARE的读取；
锁完再另做无锁SELECT会看到快照后新插入的档案，造成资格竞争。新请求若
该锁定快照没有目标身份就拒绝，原成功收据重放则不要求目标现在仍存在。

## 权限与审计

新RPC在public用于PostgREST调用，但撤销PUBLIC／anon／authenticated的EXECUTE，
仅service_role可调用；请求收据在private、RLS启用、不授予外部表权限。
SECURITY DEFINER只用于这项已经验证HTTP身份的受控转交，固定空search_path、
限定对象名，不改变整个lease表的浏览器写权限。函数也独立验证actor当前合法角色
及Auth状态，不能只依赖旧Token或前端显隐。参数中的actor只能由可信HTTP层提供。

既有审计触发器保持原定义／身份。RPC临时设置并恢复事务内JWT subject，使
LEASE_TRANSACTION_UPDATE记录真实操作者。显式转交事件与收据都在同一事务，
审计或收据插入失败会整笔回滚；HTTP和客户端不重复另记权威转交事件。

## 请求兼容与未知结果

新请求必须包含requestId、expectedSubmitterId、expectedUpdatedAt；后两项可显式
为null，旧文本归属保持原值，时间保持完整微秒。旧页面缺字段返回409要求刷新，
不得从当前数据库读值来伪造用户看到的旧版本。RPC未就绪返回503，不回退旧直接写。

客户端先持久化pending，再发送；存储失败不发送。25秒超时、断网、5xx、异常成功
响应均保留原请求ID，页面保留待确认入口，关闭／重开／刷新不把未知请求变成新转交。
首次确定拒绝可释放该请求；未知之后再遇拒绝仍保留原请求以供核对。账号切换隔离，
并发标签页有独立请求key，数据库版本与幂等锁决定实际结果。确认成功但刷新失败
单独提示，不误报为可再次执行的转交失败。本地存储不是权限依据。

## 验证与未验证范围

正式入口：`npm run test:db:lease-transfer`、对应route/client/page测试及
`npm run verify`。Verify CI新增真实PostgreSQL执行步骤，失败即检查失败。
详见[数据库回归说明](../supabase/tests/lease-transfer-safety/README.md)。

本地命令结果、浏览器链路及最终精确head CI由本批验证记录维护；在这些证据
齐备前不称为上线就绪。本说明本身不证明已运行测试。真实生产JWT发放、生产写入、
手机真机与数据库备份恢复能力未由合成夹具证明。

本地真实PostgreSQL 17.11已执行23组转交回归。独立复核发现的“新插入目标档案
未锁定”已用四连接确定性复现旧SQL错误成功，再以同一正确断言验证修复。
CAS、重复请求、资格变更测试使用真实锁等待屏障；移除成交行锁会出现两笔
竞争请求都成功，移除资格锁会使锁等待断言失败。实际迁移文件未因变异测试改变。

## 获授权后的发布顺序

1. 核对当时main／待发布commit、目标库PG版本、迁移名无冲突、原审计函数仍为
   已修复版本、现有两条触发器及policy／grant与被测基线一致。不得顺手修历史。
2. 确认可访问且适用的恢复点、目标环境授权、受限验证对象与停止条件。此前授权
   的审计计数迁移不自动授权本次迁移；没有可信恢复办法就不执行生产数据库变更。
3. 单独应用新增迁移 `20261027013818_secure_lease_submission_transfer.sql`；
   该迁移只创建新表／函数，现有业务行、策略、触发器不变。核验函数固定search_path、
   预期owner、EXECUTE ACL，以及private收据表外部不可读写。
4. 用户确认后发布已验证代码。旧标签页转交需刷新；新代码若迁移缺失会安全停止。
   原HTTP地址仍存在，但旧读写实现被替换，不保留绕过路径。
5. 仅对获授权的专用对象或明确的一次业务操作核对成功、服务端接收名、允许字段
   差异、两类审计、收据和回读。禁止新增假生产成交或反复转交真实任务做烟测。
6. 若有非预期字段／归属变化、假成功、权限异常或审计缺失，停止扩展使用，保留
   请求和证据，按下面策略处置。

## 回退与停止

- 新代码问题：可以暂停此转交接口或回退到经过审查且同样拒绝不安全写入的版本。
  不可直接恢复原“读后按ID覆盖”的实现。停止转交不应影响既有成交读取和编辑。
- 不自动DROP新收据表／函数，不清审计，不重置归属，不用整库旧快照覆盖后续正常写。
  保留新增兼容结构便于查清未知请求与继续确认。
- 若已提交的数据需要纠正，按本次请求、记录ID、原值及最新修订逐条核对后另行授权，
  已有后续合法变更的记录不得无条件反向覆盖。完整数据库恢复必须独立演练和批准。
