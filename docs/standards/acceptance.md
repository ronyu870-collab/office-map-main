# 高力国际系统 验收与发布规范

版本 0.5，2026年10月15日。仓库规范基线，保留条款的确认状态。标注“沿用”的发布纪律继续有效；已确认保护系统现有经过打磨的设计，每批涉及界面的改动提供前后对照，优先减少对其他功能的连带影响。具体验证和回退细则仍供审阅，规则编号保持稳定。

**执行状态：** 标注“沿用”或正文明确“已确认”的内容按其适用范围执行；同一条款中的建议细则仍保留建议状态。“建议”“待定”不因入库自动成为已批准的强制要求，也不授权改变现有业务、权限或整体外观。后续修改以用户最新明确要求及已确认的适用规则为准，确认新规则时同步更新状态、理由和适用范围。

验收应能回答：原有业务结果是否正确，已打磨的设计和操作是否得到保留，本次问题是否改善，失败时是否可靠，以及发布的是否是已验证版本。测试数量或参数统一程度都不能代替这些判断。

## 验收范围与结论

### A-01 按改动选择检查范围 建议

每项任务先列具体可检查结果。例如：“表头筛选与排序共用状态；清除条件恢复记录；Viewer 可读但不能编辑；手机能关闭筛选菜单。”

检查范围跟随影响面：文案调整验证文案和布局；公共组件、共享样式或公共逻辑修改，先列出全部使用页面，再逐项判断实际影响并记录检查结果；权限、数据、草稿和季度规则修改做对应完整流程验证。对共享改动，不能只验证当前页面。某页面无需额外检查时说明依据；测试范围不扩展到与本次改动无关的流程。

### A-02 验证状态与证据 建议

| 状态 | 使用条件 |
| --- | --- |
| 通过 | 在说明的版本和环境中实际执行，结果符合预期 |
| 部分通过 | 已验证一部分，同时列出剩余范围 |
| 未执行 | 尚未运行或没有所需环境、账号、工具 |
| 失败 | 实际结果不符合要求，说明影响与处理 |

每项重要结论注明验证方式、环境和数据范围。模拟数据、代码审查、组件测试和真实浏览器验证分别表述。不能把“代码看起来正确”写成“线上实测通过”。

## 界面与交互验收

### A-03 视觉与响应式 建议

影响界面的改动至少检查受影响区域的桌面和手机呈现；公共布局或导航调整增加平板宽度。建议基准如下，具体参数待审阅确认。

| 场景 | 建议基准 | 核对重点 |
| --- | --- | --- |
| 桌面 | 1440×900 | 层级、密度、列宽、菜单与固定操作区 |
| 手机 | 390×844，并检查窄屏约 360px | 溢出、触控、键盘、关闭与提交入口 |
| 平板 | 768×1024，布局调整时执行 | 导航折叠、分栏切换、遮挡 |
| 页面缩放 | 200%，关键阅读和操作区域 | 文字、焦点、内容及操作可达性 |

对照从现有实际界面提取的样式基准，核对字号、行高、颜色、间距、组件和状态；检查改动区域与相邻未改区域、同类页面之间是否协调。字号、行高或控件尺寸有变化时，在前后对照中说明所依据的现有样式，检查阅读、换行、密度和操作位置是否受影响。不得出现无理由的重复操作入口、截断关键字段、不可达按钮或遮挡输入。宽表可以在指定容器内横向滚动。新页面和后续改动沿用同一基准进行验收。 公共字号和行高改动需记录代表元素的最终计算样式；区分变量声明值、生成的 CSS 属性与浏览器实际显示值，并检查修复解析问题是否引起意外放大、缩小或换行。

### A-04 状态与键盘操作 建议

按受影响组件检查正常、加载、空结果、无权限、失败、处理中和成功状态。使用较长中文、长楼宇名、空值和零值检查布局。

弹窗、抽屉和菜单验证打开、关闭、Escape、键盘焦点及焦点恢复。失败提示要说明发生了什么及下一步可做什么，不能留下只有技术报错的死路。

### A-05 每批修改前后对照 方式已确认

已确认：每批涉及界面的改动均提供修改前后对照，供余航指出不满意的地方。执行建议：改动前保留对应版本的画面，改动后使用相同页面、视口、数据条件和操作状态进行对照，标出尺寸、颜色、间距或行为的具体变化；桌面和手机按实际影响提供对照。截图使用合成或脱敏数据；真实敏感记录只在适当权限下内部检查。交互变化可补充可点击预览或操作记录。

本轮按保留现有设计、先公共组件后页面的顺序推进。每批将前后对照与原问题、需保留的细节一起核对：原问题应改善，同时不能出现未预期的字号、换行、密度、操作位置或关联功能变化。首批先用一至两个代表场景验证，若新增不协调或破坏既有细节，先修正或撤回相关改动，再扩大到下一批；因任务需要的合理变化须说明依据。用户审阅与开发验证分别记录，前后对照不能替代功能、权限和数据检查。发布继续按当前任务与已有授权执行。没有可用浏览器或改动前画面时，明确缺少的证据，不能宣称视觉验收已完成。

## 业务与数据验收

### A-06 权限与身份 建议

涉及可见范围或操作能力时，覆盖未登录、Viewer、Editor、Admin，以及相关模拟或预览场景。验证界面入口和服务端/数据库边界，不能只检查按钮是否隐藏。

重点核对当前成交和受限历史成交、本人和他人记录、管理员操作、身份切换及旧请求晚返回。相同数据范围内 Viewer 与 Editor 的读取应一致，Viewer 的业务写入应被阻止。

### A-07 查询与导出正确性 建议

涉及查询、统计或导出时，核对筛选、排序、分页、总数与导出范围一致；使用超过单页的数据验证完整性。分页任一环节失败时，不应把部分结果标为完整成功。

保留原始数值精度，按字段正确处理单位、日期、季度、空值、零值、项目归属和同名对象。完成率写明分母、去重方式和草稿是否计入。

### A-08 草稿与提交可靠性 建议

修改填报时，按影响覆盖首次进入、保存、再次打开、失败重试、刷新恢复、切换分类、切换账号、切换季度和提交确认。

验证历史参考不会覆盖当前输入，旧请求不会覆盖新状态，冲突不会静默丢掉其他人的更新。保存成功与提交成功各有服务端结果；重复点击和重试不会生成重复业务结果。

### A-09 失败与恢复 建议

对受影响流程检查慢响应、超时、权限拒绝和读取/写入失败。恢复后允许继续，保留应保留的输入、筛选和上下文。

多步骤操作要能判断已经完成哪一步；不得把“写入成功、刷新失败”误报为整笔写入失败，也不得把关键数据缺失当成正常空数据。关键依赖未确认时不开放可能造成错写的操作。

## 性能与自动检查

### A-10 性能验收 沿用目标并建议补充记录

沿用现有性能基线中的产品目标：普通点击反馈小于 100ms，路由工作区框架出现小于 200ms，地图筛选更新小于 250ms，INP 小于 200ms。INP 用于衡量交互响应。这些是产品目标，不是当前自动测试已强制执行的统一时限。

性能改动记录冷、热访问、请求数、主要串行依赖及实际可测的耗时。噪声较大的耗时至少记录三次并看中位数，使用可比较环境。不能用结构优化、模拟耗时或单次请求证明生产提速百分比。

### A-11 仓库验证 沿用

有实质影响的代码改动须通过 `npm run verify`。相关数据库改动还需隔离回归与适用的并发、授权测试。测试证据应覆盖本次改变的行为，原有测试不得为掩盖问题而降低断言。

仓库现有自动流程验证类型、Lint、测试、数据库回归和构建；统一视觉回归等新增检查，需要单独落地后才能标为已启用。 关键页面视觉回归、公共样式与组件使用检查等后续自动化，需在实际实现并验证后更新启用状态。

## 发布与交付

### A-12 发布门槛 沿用及建议

沿用：只合并最终提交通过 Verify 的版本；预览 READY 不能替代测试通过。合并后确认内容与已验证版本一致，发布按当前任务和已有授权执行。

建议：越权、数据错写或丢失、关键流程不可用、关键验证失败，以及本次改动新引入的核心界面不可用问题，阻断发布。低影响的非阻断遗留项应写明范围与后续安排，不能隐瞒。

### A-13 上线核对 建议

确认正式项目、环境、提交版本和域名；检查适用健康接口、登录或路由入口以及新增错误日志。涉及授权时检查未登录或低权限访问仍受保护。

健康检查成功只证明其覆盖的服务正常，不能代替真实登录业务流程或性能测量。每批保留可定位的基线版本与回退方式；发现严重功能问题或破坏已确认需保留的视觉、交互细节时，按影响修复或撤回相关改动，避免继续扩大影响。回退只撤销本批相关内容并保护后续无关修改；数据库操作按已验证回退方案处理。

### A-14 交付记录 建议

每轮交付至少说明结果、主要改变、验证证据、发布状态和仍未确认的范围，并提供合并请求或对应文件入口。非平凡变更在 `CHANGELOG.md` 留下可追溯记录。

建议使用简短交付格式：

- 结果：用户现在可以完成什么。

- 改动：本轮改变了哪些行为；界面改动附修改前后对照及变化标注。

- 验证：受影响页面和流程、实际检查结果及环境；未执行项明确列出。

- 发布：分支、预览或正式站，以及对应版本。

- 遗留：尚未验证或待处理的具体事项，没有则省略。
