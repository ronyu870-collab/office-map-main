# 高力国际系统 开发与数据规范

版本 0.5，2026年10月15日。仓库规范基线，保留条款的确认状态。标注“沿用”的条款继承现有仓库纪律；已确认保护现有合理设计与功能，先完善公共组件再分批迁移，减少改动连带影响并提供每批前后对照。其余执行细则经审阅确认后纳入规范，规则编号保持稳定。

**执行状态：** 标注“沿用”或正文明确“已确认”的内容按其适用范围执行；同一条款中的建议细则仍保留建议状态。“建议”“待定”不因入库自动成为已批准的强制要求，也不授权改变现有业务、权限或整体外观。后续修改以用户最新明确要求及已确认的适用规则为准，确认新规则时同步更新状态、理由和适用范围。

本规范约束代码组织、数据访问、权限、性能和发布过程，让后续维护者能理解改动、复现验证并继续开发。

## 开工与代码组织

### E-01 从最新代码和相关规范开始 建议

开始前确认目标仓库、最新主分支和当前工作区状态；记录开发基线。发现他人未提交改动时保留其内容，采用隔离分支或工作区处理本次任务。不得用旧快照覆盖远端更新。

先读取 `AGENTS.md`、`README.md`、四类规范中已确认的条款及相关模块文档；再检查受影响代码和测试。框架或 SDK 用法按项目实际安装版本查阅官方文档，不凭旧版本印象修改。

### E-02 明确目标和变更范围 建议

动手前用简短文字说明已核实的问题、期望行为、主要影响区域和验证方式。界面治理同时记录需要保留的设计细节，区分实际缺陷、合理差异与待核实差异。新增复杂流程先形成可审阅方案；一般修复和已授权的改进直接推进，不重复请求相同授权。每批围绕一个可验证目标组织，避免将样式统一与无关的权限、数据或业务逻辑重构混在一起。

需要新增依赖、改变业务口径、改动权限或执行不可逆数据操作时，说明必要性和后果；是否需要确认，依据本次任务和已有授权判断。

### E-03 按职责组织代码 建议

| 位置 | 主要职责 |
| --- | --- |
| `src/app/` | 路由、页面组合和服务端 API 边界 |
| `src/components/` | 可复用界面与交互组件 |
| `src/hooks/` | 复用状态与客户端生命周期逻辑 |
| `src/services/` | 外部数据访问和服务调用 |
| `src/lib/`、`src/utils/` | 按现有约定放领域逻辑、通用能力与纯函数 |
| `supabase/migrations/` | 可审阅、可追溯的数据库迁移 |
| `docs/` | 已确认规则、专项设计及操作说明 |

沿用模块已有合理边界；新建目录需有明确用途。简单逻辑保持简单，多处变化或难以验证时再拆分，避免为文件长度或形式上的分层机械重构。

### E-04 公共能力复用与依赖 建议

先搜索现有组件、权限函数、数据服务、格式化和查询工具，再决定新增。重复的业务口径和权限判断应收敛到可靠的公共实现，防止各页面分别维护。按本轮已确认顺序，先完善公共组件，再分批迁移已确认需要优化的页面；抽取确有共同需求的外观和行为，保留场景差异及模块业务边界。共享组件先保持现有默认行为，必要时通过明确变体让选定页面逐步采用；调整默认值前核对全部实际影响。代码复用与修正样式解析问题都需验证现有合理外观及行为得到保留，避免一次批量替换传播变化。

新增依赖需说明用途、体积、维护状态和替代方案；仅按需要引入。更新依赖同时维护锁文件，不夹带无关的版本升级。

## 数据与权限

### E-05 身份和权限在可信边界校验 沿用及建议

沿用：业务授权须由服务端和数据库访问规则执行；隐藏按钮不能替代授权。浏览器只能使用允许公开的配置，服务端密钥不得进入客户端代码、日志或前端环境变量。

建议：统一使用已存在的有效身份与权限解析方法。真实操作者、被模拟用户、记录归属和管理员专属范围分别校验。未知角色、身份验证失败、关键权限信息缺失时拒绝受保护操作。

### E-06 数据读取范围和缓存 建议

查询应明确字段、权限、筛选、排序、分页和时间范围。存在服务端行数上限时，完整导出或统计须正确读取所有目标页；分页失败不能静默返回看似完整的部分结果。

缓存明确有效期、身份范围和失效方式，切换账号、权限或模拟身份后不复用其他范围的数据。禁止在服务端跨用户共享可变会话或用户私有查询结果。公开共享数据的缓存也需明确哪些信息允许共享。

### E-07 输入校验与业务类型 建议

关键写入在可信边界校验身份、归属、枚举、范围、单位和季度。客户端校验用于帮助用户及时纠错，服务端仍须独立验证。

核心业务对象、API 入参出参和状态使用明确类型。外部未知数据先校验再使用；避免用宽泛类型掩盖错误。历史兼容转换在边界集中处理，并保留可追踪的规则。

### E-08 写入的一致性与恢复 建议

多个写入必须共同成功的业务操作，采用事务或可靠的服务端原子操作。处理重复点击、重试和并发冲突，避免重复成交、重复提交或覆盖其他人的更新。

写入成功与界面刷新成功分别处理。保存失败保留用户输入；已提交成功但后续刷新失败时，不得引导用户盲目重复提交。涉及草稿的改动验证恢复、归属、版本和季度隔离。

### E-09 数据库迁移与生产数据 沿用及建议

沿用：Schema、RLS 和权限变更单独评估验证。不能以界面重构或性能优化为由夹带业务数据清理。

建议：数据库变更记录目的、影响对象、兼容顺序、验证和回退方式。高影响变更先在隔离环境验证；生产回填、删除或口径转换按明确授权范围执行，必要时先保留可恢复备份。迁移成功不等于业务结果已正确。

### E-10 错误处理与审计 建议

关键读取或写入失败要向调用层和用户表达，不能用空结果掩盖。确属非关键的降级可继续执行，但说明其影响并留下可定位日志。

涉及权限、导出、下载和重要写入时，检查既有审计要求。记录操作者、动作、业务对象、结果和必要上下文；日志不得包含密码、完整令牌或无必要的敏感业务内容。审计策略变化不能扩大业务权限。

## 性能与异步交互

### E-11 减少无效工作 建议

先确认瓶颈，再优化重复请求、无关串行依赖、大依赖加载、无效渲染或慢查询。按需加载尚未打开的重型界面，互不依赖的任务可并行执行。

使用慢请求、取消、切换页面和切换账号等场景验证旧响应不会覆盖新状态。优化前后保持业务结果、权限和数据完整性一致。

### E-12 性能证据 建议

性能记录区分冷启动、再次访问、网络耗时和界面处理耗时。前后使用可比较环境与数据范围；说明样本和测量方式。

请求数减少、构建成功或模拟测试通过，可以支持对应结构性结论；不能据此编造生产提速比例。数据库索引或查询改造要有查询证据，避免凭猜测增加维护成本。

## 验证与发布

### E-13 验证要求 沿用及建议

有实质影响的代码改动完成前，执行仓库 `npm run verify`；迭代可使用 `npm run check`。完整验证包括审计覆盖、类型、Lint、测试和生产构建；相关数据库变更还需专项回归。

测试优先证明用户行为、授权边界、错误恢复和数据正确性。一般可逆样式调整不必为每个实现细节新增测试，但仍需适当界面验证。为减少改动连带影响，建议修改共享组件、样式或公共逻辑前，列出全部引用页面及实际受影响的状态、行为；完成后按清单验证相关表现和流程，记录结果。既有测试通过不能替代本轮影响范围检查；未执行项须明确标记。 样式变量或工具类调整还须检查目标 CSS 属性是否实际生成并生效；以当前安装版本的解析规则为依据。字号变量使用明确的长度类型或统一语义类，不能仅凭类名存在或构建通过认定样式正确。

### E-14 分支与发布纪律 沿用

在独立功能或修复分支工作，不用主分支迭代。将同一改动和文档调整合并成可审阅的一批，完成本地检查后再推送，避免用连续碎片提交触发远端验证。

合并前确认合并请求的最终提交通过 Verify；预览部署 READY 不能替代 CI。每批记录基线提交、影响范围和回退方式，尽量组织为可独立恢复的改动；回退需保留他人后续工作，不能覆盖无关更新。发布按本次任务及已有授权执行。上线后核对项目、环境、版本、域名及健康状态，关注新增错误；发现问题按影响修复或回退。

### E-15 维护记录与交付说明 沿用及建议

沿用：非平凡的产品、代码、数据库、性能和基础设施变更，同批更新 `CHANGELOG.md`，说明改变、原因、影响、验证及遗留工作。

建议：向用户交付时先写结果，再写改了什么、如何验证、当前是否上线及仍未确认的部分。已确认每批涉及界面的改动提供修改前后对照，供余航提出意见；具体对照方式见 A-05。区分计划、已实现、已验证和已发布，不能混写。复杂逻辑解释业务原因和关键取舍，让下一位维护者能继续工作。

## 规范执行方式

### E-16 文档入口与冲突处理 建议

四类规范位于 `docs/standards/`；`README.md` 提供系统介绍、开发启动和文档索引，`AGENTS.md` 明确任务前的阅读、执行和验收要求。界面任务还须核对现有公共组件、样式变量及从实际页面提取的样式基准；后续新增和修改沿用已确认的定义。基准及组件变体调整时同步更新规则、确认状态和适用示例，使文档、公共实现与页面保持一致。

执行当前任务时，以用户明确的最新要求和已确认的适用规则判断范围。草案与历史变更记录不自动覆盖现行规则；对会影响业务或数据的冲突，先说明具体差异并解决。普通实现选择由开发者自主完成，避免把规范变成反复审批。
